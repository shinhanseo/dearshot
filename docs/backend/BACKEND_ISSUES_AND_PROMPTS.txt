0. 사용 방법
================================================================================

이 파일은 DearShot 백엔드를 작은 Issue와 PR로 나누어 AI와 함께 구현하기 위한
실행 문서다. B-01부터 순서대로 진행한다.

각 작업 순서:

1. [ISSUE BODY]를 GitHub Issue에 복사한다.
2. 표기된 브랜치를 main 최신 상태에서 생성한다.
3. [IMPLEMENTATION PROMPT]를 AI에게 전달한다.
4. AI가 테스트와 검증을 끝내면 Draft PR을 만든다.
5. [REVIEW PROMPT]를 새 AI 작업 또는 별도 검토 단계에 전달한다.
6. 발견된 문제를 같은 브랜치에서 수정한다.
7. CI 통과 후 Squash merge하고 브랜치를 삭제한다.

한 번에 둘 이상의 Issue를 구현하지 않는다. 단, B-13 이후에는 독립적인 B-16을
병렬 진행할 수 있다.

모든 Issue 공통 완료 조건:

- Issue 범위 밖 기능을 구현하지 않는다.
- docs/openapi.yaml을 HTTP 계약의 기준으로 사용한다.
- 계약 변경 시 docs/API.md와 docs/openapi.yaml을 함께 수정한다.
- 기존 계약을 임의로 완화하거나 테스트를 삭제하지 않는다.
- DB 변경은 migration으로 작성한다.
- 토큰, 이미지 경로, 위치 좌표, 개인정보를 로그에 출력하지 않는다.
- 환경변수와 비밀키를 저장소에 커밋하지 않는다.
- npm run typecheck, npm run build, 관련 테스트를 실행한다.
- 변경 파일과 검증 결과를 PR 설명에 기록한다.
- PR 본문에 "Closes #이슈번호"를 넣는다.

브랜치 공통 규칙:

- main에서 분기한다.
- 한 브랜치에는 한 Issue만 포함한다.
- 무관한 포맷팅과 리팩터링을 섞지 않는다.
- 생성 코드와 lockfile을 제외한 변경이 약 500줄을 크게 넘으면 분리를 검토한다.

[ISSUE BODY]

## 목표

OAuth 공급자와 무관한 DearShot 인증 기반과 게스트 인증을 구현한다.

## API

POST /auth/guest
POST /auth/refresh
POST /auth/logout

## 작업

- Access Token 발급·검증
- Refresh Token 생성·회전·폐기
- Refresh Token hash 저장
- Bearer 인증 middleware
- MEMBER, GUEST, ADMIN 구분
- installationId 기반 게스트 생성
- 재사용된 Refresh Token 탐지

## 완료 조건

- 게스트가 AI API용 인증 주체를 얻는다.
- 게스트는 회원 전용 API를 사용할 수 없다.
- Refresh Token 원문은 DB에 저장하지 않는다.
- 이전 Refresh Token 재사용 시 토큰 계열을 폐기한다.
- 만료·변조 토큰은 401을 반환한다.

[IMPLEMENTATION PROMPT]

DearShot GitHub Issue B-05만 구현해.

브랜치: feat/auth-foundation

docs/API.md와 openapi.yaml의 게스트, refresh, logout 계약을 구현해.
Google과 Kakao 로그인은 이번 범위가 아니다.

보안 요구사항:
- Access Token은 충분히 강한 환경변수 키로 서명한다.
- issuer, audience, subject, principalType, exp를 검증한다.
- Refresh Token은 암호학적으로 안전한 random 값으로 생성한다.
- DB에는 SHA-256 hash와 token family만 저장한다.
- 회전된 토큰 재사용 시 같은 family를 모두 폐기한다.
- Authorization과 token 원문은 절대 로그에 남기지 않는다.
- installationId는 광고 ID나 하드웨어 ID가 아닌 앱 생성 UUID다.

필수 테스트:
- 게스트 생성
- 정상 Access Token
- 만료·변조·잘못된 audience Token
- Refresh Token 회전
- 회전 이전 Token 재사용
- 로그아웃 후 재발급 실패
- 게스트의 회원 전용 접근 거부

모든 검증 명령을 실행하고 결과를 보고해.

[REVIEW PROMPT]

B-05 PR을 인증 공격자의 관점에서 검토해.

확인 항목:
- JWT decode만 하고 signature를 검증하지 않는지
- issuer, audience, algorithm 고정 누락
- Refresh Token 원문 저장·로그 출력
- token family 재사용 탐지 우회
- 회전 과정의 트랜잭션·경쟁 조건
- 게스트가 MEMBER나 ADMIN 권한을 얻는 경로
- installationId만으로 기존 게스트 탈취 가능성
- 탈취된 Refresh Token 폐기 범위

Critical·High 문제는 테스트를 추가하고 수정해.
